============================================================
SCOPE DECISION — DISCLOSED PER REQUIREMENT #15
============================================================

The master brief's tool list (get_check_in_context, save_ai_analysis,
create_provider_alert, etc.) implies agents calling live function tools
mid-run, using @function_tool. This implementation does NOT do that.

Instead: all three agents are pure structured-output reasoners — each
receives context the orchestrator already gathered (as a plain string),
and returns validated JSON (output_type=<Pydantic model>). ALL database
writes (agent_runs, agent_actions, follow_up_tasks, risk_assessments,
risk_reasons, alerts) happen in orchestrator/checkins.py Python code
AFTER the safety gate, never via a live LLM-invoked tool call.

Why: zero API credits mean none of this can be live-verified regardless
of approach. Live tool-calling mid-agent-run is a materially larger trust
surface (a misbehaving agent could directly trigger a DB write) for no
testable benefit right now, and is harder to keep within the DI/mocking
requirement without deeper, currently-unverifiable SDK behavior (tool
invocation semantics, approval flows, etc. were not inspected — the
diagnostic passes covered Agent/Runner/ModelResponse only, per your
explicit "no broad diagnostic cycle" instruction). This is a genuine
architectural simplification, not a hidden one. If you want true
agentic tool-calling, that's a real follow-up, not a small patch on
top of this.

This does NOT weaken any of your explicit safety requirements: rule
engine stays authoritative, ClinicalSafetyAgent + the deterministic
backstop still gate every follow_up_task, bounded turns/timeouts still
apply, and the audit trail (agent_runs/agent_actions) is still complete
— it just gets written by orchestrator code instead of by the agents
themselves.
